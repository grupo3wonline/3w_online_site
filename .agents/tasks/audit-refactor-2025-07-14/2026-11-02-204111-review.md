# Hardening de segurança, dark mode e página de cookies para 3W Online

Esta PR adiciona quatro composables de segurança/UX novos (`useDebounce`, `useCSRFToken`, `useHoneypot`, `useDarkMode`), protege os quatro pontos `v-html` das ferramentas com DOMPurify, endurece os cabeçalhos HTTP em `.htaccess`, adiciona a página `/cookies` com rota e link no rodapé, e cobre tudo com 23 testes Vitest passando. A abordagem é cirúrgica: apenas 5 arquivos de ferramentas (de 126+) foram tocados, e em todos eles apenas importação de DOMPurify e uma chamada de sanitização — nenhuma lógica de negócio alterada. Watch for: o token CSRF é armazenado em `localStorage` e não é uma proteção real contra CSRF (o formulário não posta para um servidor, então isso não é crítico), e `useDarkMode` cria estado reativo isolado por chamada — funciona porque apenas `AppNavbar` usa o toggle.

**Verdict**: APPROVED

---

## High-level view

`useDarkMode` lê `localStorage` no `onMounted` com fallback para `prefers-color-scheme`. O estado `isDark` é local a cada chamada — não é singleton. Se outro componente chamar `useDarkMode()` e ler `isDark.value`, não verá atualizações disparadas pelo toggle da `AppNavbar`. Funciona hoje porque apenas `AppNavbar` usa o toggle, mas o padrão é frágil para extensão futura.

O toggle de dark mode na `AppNavbar` usa `fa-moon`/`fa-sun` com `aria-label` dinâmico em pt-BR e foco acessível via `focus:ring-2`. A preferência persiste em `localStorage` na chave `'theme'`.

O hardening do formulário em `Contact.vue` combina três camadas independentes: o honeypot bloqueia bots que preenchem campos ocultos, o debounce de 300ms evita disparos duplicados em cliques rápidos, e o flag `isSubmitting` desabilita o botão enquanto o envio está em curso. O token CSRF adicionado (`<input type="hidden" name="_csrf">`) não constitui proteção real contra CSRF — `localStorage` não é enviado automaticamente em requisições cross-origin, mas o formulário também não posta para um servidor backend (abre WhatsApp via `window.open`), então a ausência de validação server-side do token não é um gap crítico.

O `v-html` em `ConversorMarkdown` e `ValidadorRegex` processa entrada direta do usuário — esses são os pontos de XSS mais importantes e estão corretamente sanitizados. `CalculadoraPitagoras` e `CalculadoraFracao` geram HTML internamente a partir de operações matemáticas, sem entrada de usuário nos campos interpolados — a sanitização é belt-and-suspenders mas inofensiva, e DOMPurify permite os elementos HTML padrão (`<strong>`, `<br>`, `<sup>`) usados nesses componentes.

Os 23 testes cobrem os quatro composables novos, `AppBreadcrumb`, `CookieBanner`, e o fluxo de segurança de formulários. O build passa com zero erros TypeScript sobre 353 módulos.

<summary>Detalhes</summary>

### Estado não compartilhado de useDarkMode

Cada chamada a `useDarkMode()` instancia um novo `ref(false)` local. O `applyTheme` muta `document.documentElement.classList` e `localStorage`, não uma store compartilhada. Um segundo componente que chamar `useDarkMode()` e ler `isDark.value` não verá o estado atualizado pelo toggle de `AppNavbar` até que seu próprio `onMounted` execute. **Confirmado** como limitação de design — não causa bug no estado atual, mas tornaria a expansão para múltiplos consumidores propensa a dessincronização. O padrão mais robusto seria um `ref` module-level ou store Pinia.

### Proteção XSS nos pontos v-html

`ValidadorRegex` constrói o HTML de highlight interpolando diretamente o texto do usuário:
```js
highlighted = highlighted.replace(match, `<mark ...>${match}</mark>`)
```
Sem sanitização, um texto como `<img src=x onerror=alert(1)>` seria injetado no DOM. O `DOMPurify.sanitize(highlighted)` **confirmado** na linha 106 fecha esse gap. DOMPurify preserva `<mark>` e as classes Tailwind no atributo `class` por default.

`ConversorMarkdown` converte Markdown para HTML via parser próprio e depois sanitiza com `DOMPurify.sanitize(markdownToHTML(markdown.value))`. Markdown com HTML literal (ex.: `<script>`) é neutralizado. **Confirmado**.

`CalculadoraPitagoras` e `CalculadoraFracao` constroem HTML de explicação matemática a partir de valores numéricos calculados pelo próprio código — nenhum campo interpolado provém de `ref` atualizado por input direto do usuário. A sanitização é redundante mas inofensiva: DOMPurify não strips `<strong>`, `<br>` ou expressões matemáticas. **Confirmado** sem risco de regressão.

### Formulário Contact.vue: três camadas de proteção

```
click → form submit
  └─ debouncedSubmit (300ms delay)
       ├─ isBot.value === true → return (honeypot ativado)
       └─ handleSubmit()
            ├─ isSubmitting = true  (botão disabled)
            ├─ validação de campos
            └─ window.open(WhatsApp URL)
               └─ finally: isSubmitting = false
```

O honeypot (`<input style="position:absolute;left:-9999px...">`) está oculto visualmente e com `tabindex="-1"` e `aria-hidden="true"`. O guard `if (isBot.value) return` dentro de `debouncedSubmit` descarta o submit silenciosamente — comportamento correto para não alertar o bot. `resetHoneypot()` é chamado após submit bem-sucedido. **Confirmado**.

O token CSRF é lido via `getToken()` a cada render do campo `<input type="hidden" name="_csrf">`. O valor vai no body do form, mas o form não faz fetch para um servidor — abre WhatsApp. `validateToken` nunca é chamado nesse fluxo. A presença do campo é inofensiva, mas a proteção é nominal enquanto não houver backend. **Confirmado** como limitação conhecida (ver Issues).

### Cobertura de testes

23 testes em 7 arquivos, todos passando. O `useDarkMode.test.ts` testa `toggleDark()`, persistência no localStorage, e a leitura do valor. O aviso `onMounted is called when there is no active component instance` é esperado em testes unitários do composable fora de um componente — não causa falha.

O que não está testado: `ValidadorRegex` com input HTML malicioso (cobertura de integração do DOMPurify), o fluxo completo de submit do `Contact.vue` com honeypot ativado via test de componente montado, e a renderização da página `Cookies.vue`. Esses ausências não bloqueiam aprovação dado que as unidades individuais (honeypot, debounce, CSRF) estão testadas.

### Integridade das 126+ ferramentas

Apenas 5 arquivos em `src/components/tools/` foram modificados, confirmado via `git diff --stat`. Os 4 componentes com DOMPurify receberam cada um exatamente um import e uma chamada `.sanitize()` no ponto de atribuição. `BaseInput.vue` recebeu apenas `autocomplete="off"`. Nenhuma lógica de negócio alterada. **Confirmado**.
