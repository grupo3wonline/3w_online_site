# 62 Soluções Digitais: catálogo + componentes integrados ao site

This branch delivers the full "Soluções" feature: a `/solucoes` catalog page with 62 individual digital tools, each reachable at `/solucoes/<slug>`, wired into a navbar dropdown, backed by a lazy-loaded component layer. The 62 components were ported from standalone Vue and React apps (and 4 plain-HTML stubs) into self-contained SFCs under `src/components/solucoes/`. `SolucaoLayout` wraps each tool the way `ToolWrapper` wraps tools; `SolucaoView` performs the same slug→component lookup.

Watch for: **static route table instead of a `:slug` param** (works correctly, but means adding a 63rd solution requires touching 4 files; see Issues); **FEAT-002 and FEAT-003 findings fields are empty** (agents skipped recording verification output, but build and tests pass on direct re-run — confirmed).

**Verdict**: APPROVED

## High-level view

`SolucaoView` resolves the active tool by parsing `route.path.split('/').pop()` rather than reading `route.params.slug`, because the 63 routes in `solucoes.ts` use fully-qualified hardcoded paths instead of a single parameterized route. This is documented in a code comment and works correctly for all current paths. The tradeoff is that adding a new solution requires a new entry in solucoes.ts, `solucoesMap`, and `solutionMeta` — three places instead of two.

Four route names in `tools.ts` overlap with names the solucoes router would otherwise generate (`AnalisadorTexto`, `ModificadorTexto`, `DivisorTexto`, `GeradorGradiente`). The solucoes router appends a `Solucao` suffix to each. A programmatic check against the full `tools.ts` name list confirms zero runtime collisions.

The `AppNavbar` desktop dropdown follows the `servicesOpen` pattern: `mouseenter`/`mouseleave`, `Transition name="dropdown"`, white card with shadow, `@click` to close on link click. Mobile gets a flat `mobileLinks` entry that links directly to `/solucoes`; category drilling happens via the chip filter on the catalog page rather than a nested mobile dropdown — consistent with the Ferramentas mobile treatment.

`Solucoes.vue` reads `?cat=` through a computed `catParam` with a `watch` to react to programmatic navigation, and `selectCat` calls `router.replace` to keep the URL in sync when a chip is clicked. Direct URL navigation with a preset category works correctly in both directions.

### Hardcoded route table and slug extraction

The 63 routes in `solucoes.ts` each hard-code their full path (`/solucoes/calculadora-imc`, etc.). This means Vue Router never populates `route.params.slug`. `SolucaoView` handles this explicitly:

```ts
// Routes in solucoes.ts use hardcoded paths (/solucoes/<slug>) without a :slug param,
// so we derive the slug from the last path segment as a fallback.
const slug = computed(() => (route.params.slug as string) || route.path.split('/').pop() || '')
```

For all 62 current paths the last segment is the slug, so the lookup in `solucoesMap` and `solutionMeta` succeeds. A trailing slash (`/solucoes/calculadora-imc/`) would produce an empty string from `pop()`, falling through to the "Em breve" placeholder — not a user-visible issue in a Vite SPA with `createWebHistory`, but worth knowing.

A single `/solucoes/:slug` route with a catch-all for 404 would eliminate this workaround, reduce `solucoes.ts` from 390 lines to ~20, and make `route.params.slug` available to any future child component that needs it.

### qrcode ambient type declaration

`vite-env.d.ts` adds a hand-written ambient declaration for `qrcode` (which ships no bundled TypeScript types). The shape `export default { toCanvas }` matches how both `code-gen.vue` and `qr-code-pro.vue` consume it. The build confirms the declaration resolves without errors.
